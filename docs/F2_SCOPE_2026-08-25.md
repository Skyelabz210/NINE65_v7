# F-2 scope — `mod_switch_down_dual`

Constant-time finding F-2, scoped 2026-08-25. Every number below was measured in
this session on a 4 vCPU shared container @ 2.80 GHz. Where something is derived
rather than measured, it says so.

Companion: `docs/CT_VERIFICATION_PLAN.md` §4.2 (the finding), §4.8 (F-1, closed
the same way this proposes to close F-2).

---

## 1. The finding

`RNSFHEContext::mod_switch_down_dual` — `crates/nine65/src/ops/rns_fhe.rs:3903`.

| contrast | class A | class B | gap | t_signal | t_control |
|---|---|---|---|---|---|
| all-zero vs uniform coefficients | 18.05 ms | 53.50 ms | **2.96×** | 616.3 | 0.54 |

Not a percentage — a factor of three, and the largest measured timing dependence
in the codebase.

**Cause.** The per-coefficient kernel leaves residue space:

```rust
// Reconstruct v mod M_level
let main_residues: Vec<u64> = poly.main.iter().map(|limb| limb[i]).collect();
let v_m = self.rns.to_u256_level(&main_residues, num_poly_primes);
let v_centered = SignedU256::center(v_m, m_level, m_half);
let (mut q_mag, rem) = v_centered.mag.div_mod_u64(q_last);
```

Three magnitude-dependent steps: a CRT reconstruction into a positional `U256`,
a centering comparison against `M/2`, and a long division over the reconstructed
magnitude. Then one `mod_u64` per output lane, also over that magnitude.

This is a **Rule 2 violation** — no synthetic emissions in residue space — and
the leak sits exactly at the site where the code stops being residue-native.
That is the substantive point: F-2 is evidence *for* the architecture. The leak
is in the positional domain the code enters after abandoning the lanes.

## 2. Reachability — measured, and it changes the priority

The function was instrumented with an `eprintln!` and a real workload run:

| workload | F-2 hits |
|---|---|
| `cargo test -p nine65 --lib --release` (764 tests) | **0** |
| encrypt / add / mul / decrypt across all four configs | **0** |

**It is never reached in normal operation.** Why: nothing moves the basis.
`should_two_stage_rescale` is hardcoded `false`, and `mul_dual_public` rescales
by `Δ = M_level/t` while leaving `level` untouched, so `add_dual`'s level
alignment is always a no-op.

It is **not** dead code, though. Verified reachable through the public API:

```
fresh ct level=5 main_lanes=5
!!!F2_REACHED mod_switch_down_dual lanes=5     <- c0
!!!F2_REACHED mod_switch_down_dual lanes=5     <- c1
REACHABLE: switched to level=4 lanes=4
```

`mod_switch_ct_to_level` → `mod_switch_ct_down` → `mod_switch_down_dual`, and
`add_dual` reaches the same chain whenever two ciphertexts have different levels.

**So: unreached today, reachable by any caller, and it would become hot the
moment a level ladder is revived.** Earlier framing of F-2 as "the biggest
number on the board" was accurate as a measurement and misleading as a priority.
This corrects that.

---

## 3. The replacement already exists, and it is strictly better

`exact_modulus_switch_drop_poly` (`rns_fhe.rs:5246`) computes a lane drop with no
reconstruction, via `align_and_drop_lane` — which was made constant-time when
F-1 was closed (§4.8: t = 0.96 / 0.45 against controls 1.16 / 0.11). It writes
**both** main and anchor lanes lanewise.

Measured on the identical polynomial (secure_192, n=16384, 5 main + 10 anchor):

| path | median | constant-time |
|---|---|---|
| `mod_switch_down_dual` (reconstructs) | **104.316 ms** | no — 2.96× |
| `exact_modulus_switch_drop_poly` (lanewise) | **1.867 ms** | yes |

**56× faster and constant-time.** This is not a security-versus-speed tradeoff.
The residue-native path wins on both axes; the only thing standing in the way is
semantics.

## 4. The gap is semantic, not implementational

|  | `mod_switch_down_dual` | `exact_modulus_switch_drop_poly` |
|---|---|---|
| representative | centered, signed | unsigned, `[0, M)` |
| division | `round(X / q_last)` | `floor((X − r_k) / q_k)`, exact |
| method | reconstruct → divide | lanewise, no reconstruction |

Two differences to close.

### 4a. Rounding — cheap, and no reconstruction needed

`round(X/q_k) = floor(X/q_k) + [r_k ≥ q_k/2]`, where `r_k = X mod q_k` is the
**dropped lane's own residue** — already in hand as `dropped[c]`, requiring no
reconstruction at all. The correction is a single conditional `+1`, and it must
be applied with a branchless mask, because `[r_k ≥ q_k/2]` is a comparison on
ciphertext-derived data and would otherwise reintroduce exactly the branch that
caused F-1 (§4.8). `BarrettContext::geq_mask_u64` already provides it.

Low risk.

### 4b. Centering — this is the real question

Write `M = q_k · M'`, `X ∈ [0, M)`, `f = floor(X / q_k)`.

For `X > M/2` the centered value is `X_c = X − M`, and

```
floor(X_c / q_k) = floor(X/q_k) − M' = f − M'
```

**Derived, not yet tested:** modulo `M'`, `f − M' ≡ f`. So for the **surviving
main lanes, centering is a no-op** — the unsigned lanewise result is already
congruent to the correct signed result.

The anchor lanes are a different matter. They live outside `M'`, so
`(f − M') mod a_j ≠ f mod a_j` in general, and the sign decision is visible
there. Deciding `X > M/2` from residues is the classic RNS magnitude-comparison
problem, and it is the one genuinely hard part of this change.

The rounding conventions also differ at the boundary: the current code rounds
`|X_c|/q_last` half-up on the *magnitude* (half-away-from-zero), while the
unsigned form rounds half-up on `X`. These agree mod `M'` except possibly at
exact-half boundaries. **Both claims in this section need an exhaustive
differential test before anything is built on them — that is step 1.**

## 5. Options

**A. Adopt the lanewise path + rounding correction.** Closes the leak, removes
the Rule 2 violation, 56× faster. Requires establishing that anchor-lane
consumers tolerate the `M'` offset, or that the sign can be recovered.

**B. Recover the sign from the winding index `k`.** The CRAM answer — magnitude
is a read of carried identity, `X = γ + k·M`, not a reconstruction.
Architecturally correct and the only option that closes centering *properly*.
Needs a residue-space comparison against `M/2`, which is real work.

**C. Fence it.** Since it is unreached, make `mod_switch_down_dual` return a
typed error, or `#[deprecate]` it toward the lanewise primitive, and document
that the level ladder is retired. Removes the exposure without a scheme change.

**D. Record and defer.** Accurate, no code change.

### Recommendation

**A, staged, gated on step 1 — with C as the immediate move if the ladder stays
retired.**

The reasoning: F-2 is unreached, so nothing is burning. But the replacement is
already written, already constant-time, and 56× faster, which makes A unusually
cheap for what it buys. The only unknown is the anchor-lane semantics, and that
unknown is a *bounded* investigation, not open-ended research. B is the right
long-term answer and should not be attempted before A's audit tells us whether
it is even needed.

If the level ladder is genuinely retired for good, C is honest and costs an
afternoon — and it is strictly better than leaving a 2.96× leak behind a public
API nobody calls.

## 6. Plan

| # | step | output | risk |
|---|---|---|---|
| 1 | Exhaustive differential test: lanewise+rounding vs `mod_switch_down_dual`, small moduli, every `X ∈ [0, M)`, main **and** anchor lanes compared separately | the §4b claims confirmed or refuted | none — test only |

### Step 1 result — 2026-08-30

`ops::rns_fhe::tests::f2_step1_lanewise_rounding_vs_mod_switch_down_dual_exhaustive`.
Exhaustive over a 3-main-lane chain (`n=4`, primes `[17, 41, 73]`, `M = 50881`), the
real, canonical `n < 16384` anchor primes attached unchanged, every `X ∈ [0, M)`.

**Floor/no-reconstruction claim (first half of §4b): CONFIRMED, unconditionally.**
`f − M' ≡ f (mod q_i)` holds for every `X`, exactly as derived — no exceptions.

**Rounding correction (§4a), as literally stated: REFUTED, narrowly and exactly.**
The naive `[r_k ≥ q_k/2]` correction, applied uniformly with no branch information,
mismatched `mod_switch_down_dual` on 1394 / 101762 main-lane comparisons (1.37%) —
but **every single mismatch** is confined to `X > M/2` with `X mod q_k ∈
{⌊q_k/2⌋, ⌊q_k/2⌋+1}` (asserted per-mismatch in the test, not just aggregate-counted).
Mechanism: `mod_switch_down_dual` rounds the *signed* value half-away-from-zero
(symmetric under negation); the naive correction rounds the *unsigned* `X` half-up
(not symmetric under negation). The two conventions provably agree everywhere except
these two residues out of `q_k`, adjacent to `q_k`'s own half — precisely the "exact-half
boundary" this doc's §4b already flagged as open. **Not a dead end**: the correction
needs a second, branch-aware term (or a convention change to round-half-away-from-zero
throughout), not a redesign.

**Anchor lanes: CONFIRMED to need real work, and more completely than §4b guessed.**
0 / 178080 anchor comparisons matched above `M/2` with no correction applied — not
"generally mismatches", *always* mismatches once `X > M/2`. Anchor lanes get zero
benefit from the free `M'`-periodicity main lanes have; the `M'` offset (or the
winding-index route, option B) is not optional for them.

**Consequence for the plan**: option A survives step 1, revised — the rounding fix is
narrower and better-understood than §4a assumed (2 residues out of `q_k`, not a vague
boundary), but is a real second fix, and anchor-lane centering is still unsolved and
still the hard part per §4b. Step 2 (audit anchor-lane readers) is unblocked to proceed;
step 3 (build the new primitive) should fold in the corrected rounding term before
anchor-lane centering is even attempted, since main lanes are now fully closed.
| 2 | Audit every reader of anchor lanes after a mod-switch; determine whether the `M'` offset is observable | go / no-go for A | none — read only |
| 3 | If go: add the branchless rounding correction to `exact_modulus_switch_drop_poly` behind a flag | new primitive, unwired | low |
| 4 | Differential-test the new primitive against the old across all four configs, both modes | equivalence evidence | none |
| 5 | Swap `mod_switch_down_dual`'s body to delegate; keep the signature | leak closed | **medium** — public API behaviour |
| 6 | Re-run F-2's two dudect tests; move them from `open-findings` to `dudect-blocking` in `ct_verification.yml` | F-2 closed, gate flipped | none |

Step 1 is decisive and cheap. If it refutes §4b, A dies and the choice is B or C.

**Do not skip step 2.** The whole reason F-1's first fix attempt failed was
acting on a plausible mechanism before measuring it.

## 7. Risks

- **Semantic drift.** The two functions do not compute the same thing today. Any
  swap must be justified by step 1's exhaustive test, not by inspection.
- **Public API.** `mod_switch_down_dual`, `mod_switch_ct_down` and
  `mod_switch_ct_to_level` are all `pub`. Changing behaviour is visible to
  callers outside this repo.
- **The tests that would catch a mistake are mostly retired.**
  `test_mul_dual_public_with_mod_switch` and the level-ladder suites in
  `basis_invariance.rs` / `residue_space_ciphertext.rs` are `#[ignore]`d as
  VESTIGIAL/RETIRED. Step 4 must bring its own coverage; it cannot lean on
  what is already there.
- **No CI.** No workflow in this repository has run since 2026-02-27, so any
  gate added here must live in `cargo test` to mean anything
  (`docs/CT_VERIFICATION_PLAN.md` §5).

## 8. The leak itself, closed separately — 2026-09-04

This document's plan (options A/B/C, §5-6) is about *replacing*
`mod_switch_down_dual` with the lanewise primitive — a semantic change that
is still exactly as open as when this was written: step 1 (§6) is done, steps
2-6 are not, and the anchor-lane centering question in §4b is still real work.
None of that changed.

What closed instead, without touching semantics, is the *timing leak itself*.
Issue #72 named it explicitly: "Replace `U256::div_mod_u64` with CT
alternative." That is a strictly narrower move than this document's plan —
same function, same (quotient, remainder) contract, only the division's
implementation changes from hardware limb division to a fixed-256-iteration
constant-time form (`U256::div_mod_u64_ct`). `mod_switch_down_dual` now calls
it. Full writeup: `docs/CT_VERIFICATION_PLAN.md` §4.9.

This does not make the plan above moot. `mod_switch_down_dual` is still
104ms-class per coefficient-batch against the lanewise primitive's 1.9ms —
56x is still on the table if the level ladder is ever revived, and the CT fix
does not recover any of that. It only means the *security* half of this
document's motivation (the 2.96x timing leak) is settled independently of the
*performance* half, and a future decision to pursue option A is no longer
also carrying "and it's not constant-time yet" as a reason to hurry.
