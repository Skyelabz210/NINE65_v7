## Operating rules

The coordinator owns the combined ledger and integrates reviewed work. Implementation workers use separate worktrees; heavyweight builds are serialized. K remains derived on demand; source observations must be authentic; no scalar oracle or Garner/MRC emission substitutes for the requested residue computation. Product-state, arithmetic, encrypted, stochastic and continuum semantics retain their distinct premises.

Each candidate records ancestry, exact source/observation/consumer, assumptions, ambiguity, transition, forward benefit, return benefit, verified related work, decisive test, cost scope, evidence status and next action. Potential and readiness are scored separately. Counterexamples trigger a repair search, not silent deletion or an automatic whole-framework rejection.

The live referenced task remains unavailable because read_thread is not exposed. Its contents are not inferred. This is a coverage dependency and does not stop independent work.

## Acceptance

New mathematical claims need explicit premises and independent review; checked claims need fresh Lean builds and axiom audit. Runtime claims need actual producer-to-consumer execution with negative source/frame/epoch/capacity controls. Encrypted claims need an admitted ciphertext execution or a recorded refusal; mathematical correctness does not change security admission. Performance evidence charges setup, widths, observations, conversions, memory and encrypted work separately.

A completed bounded campaign records every selected candidate as supported, repaired, refuted, conditional or blocked by a named dependency. It supplies reviewed local patches, reproducible experiments, a deduplicated proof inventory and a ranked continuation backlog. It does not claim all future applications have been exhausted.
